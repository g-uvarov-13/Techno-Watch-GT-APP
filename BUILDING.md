# Сборка Android и подпись APK

Все команды ниже выполняются относительно корня публичного пакета. `android/` — Gradle-проект; `tools/` — отдельные Python-инструменты. Для сборки APK достаточно включённых исходников и ресурсов; ключ OpenRouter, Bluetooth и пересоздание изображений не нужны.

## Зависимости

| Компонент | Значение проекта |
| --- | --- |
| JDK | Java 17; один и тот же выбранный JDK для Gradle и проверки |
| Gradle wrapper | 9.1.0, версия закреплена в `gradle-wrapper.properties` |
| Android Gradle Plugin | 9.0.1 |
| Android SDK | Platform 36; Build Tools, совместимые с выбранным AGP |
| `compileSdk` / `targetSdk` | 36 / 36 |
| `minSdk` | 26 (Android 8.0) |
| `versionName` / `versionCode` | 1.0.1 / 102 |
| namespace / `applicationId` | `app.gtdial.lab` |
| Основная библиотека | `androidx.core:core:1.17.0` |
| Python для автономных инструментов | Python 3.9 или новее; для инструментов отрисовки дополнительно Pillow |

Gradle получает зависимости из Google, Maven Central и Gradle Plugin Portal. Первая сборка обычно требует сети для wrapper/плагина/библиотек. `--offline` работает только после заполнения соответствующего кеша; слово «offline» в имени вспомогательного скрипта не гарантирует отсутствие загрузок.

В `android/local.properties` можно указать `sdk.dir` для своей установки SDK. Этот машинный файл не должен попадать в Git. Либо задайте стандартное окружение Android SDK. `JAVA_HOME` должен указывать на корень выбранного JDK 17. Не добавляйте в публичный скрипт путь домашнего каталога сопровождающего.

## Сборка без секретов

На Linux/macOS или в Linux-среде WSL:

```sh
cd android
./gradlew --no-daemon clean assembleDebug lintDebug
```

Если архив не сохранил исполняемый бит wrapper, запустите через `bash ./gradlew` с теми же аргументами. На Windows используйте переносимый PowerShell-скрипт из публичного пакета, если он включён и настроен для вашей среды:

```powershell
.\android\build-offline.ps1 clean assembleDebug lintDebug
```

Публичный PowerShell-wrapper запускает Gradle через WSL. В выбранной WSL-среде должны быть Linux JDK 17 и Android SDK с Linux-инструментами. При необходимости укажите `CHASOVOY_JAVA_HOME` и `CHASOVOY_ANDROID_SDK_ROOT`: wrapper передаёт эти значения как `JAVA_HOME` и путь SDK в Linux-окружение. Эти переменные описывают вашу среду, секретов не содержат; используйте пути, доступные WSL. Если они не заданы, предварительно настройте JDK/SDK в самой WSL-среде.

Не назначайте Windows-бинарники JDK/SDK в Linux-окружение. Для Windows документированный путь сборки — PowerShell-wrapper через WSL; прямой `gradlew.bat` не входит в этот путь.

Всегда передавайте `clean assembleDebug lintDebug` явно. Не запускайте `build-offline.ps1` без аргументов. Тесты разрешены только отдельным прямым запросом в текущей задаче. Frontend/JavaScript-сборки для Android APK не нужны.

Ожидаемый debug APK: `android/app/build/outputs/apk/debug/app-debug.apk`. Результаты lint находятся в `android/app/build/reports/`. Debug-подпись годится для локальной работы; её нельзя выдавать за согласованную постоянную подпись публичного выпуска.

## Подпись публичного выпуска

Используйте отдельный закрытый ключ выпуска. Не кладите keystore, пароль, экспорт закрытого ключа или файл signing properties в репозиторий/публичный архив. Резервную копию ключа храните отдельно: без прежнего ключа обычное обновление установленных APK невозможно.

Публичная конфигурация использует переменную `CHASOVOY_SIGNING_PROPERTIES`, которая указывает на приватный `.properties`. Сам файл содержит:

```properties
storeFile=<путь к приватному keystore>
storePassword=<приватное значение>
keyAlias=<псевдоним ключа>
keyPassword=<приватное значение>
```

Это описание полей, не готовый файл с рабочими секретами. Формат Java properties требует правильного экранирования Windows-путей; удобнее использовать `/`. Не передавайте пароли аргументами Gradle или командной строкой `keytool`: они могут остаться в истории/списке процессов. Создание нового ключа лучше выполнять интерактивно, сохраняя его вне рабочей копии. Псевдоним ключа и субъект сертификата выбирает владелец выпуска; не включайте домашний адрес и другие личные сведения.

`storeFile` и значение `CHASOVOY_SIGNING_PROPERTIES` должны быть понятны ОС, в которой работает Gradle. При PowerShell→WSL нужно преобразовать оба пути либо использовать WSL-native paths для файла и содержимого. Конвертация пути к `.properties` не конвертирует автоматически `storeFile` внутри него.

После настройки приватного файла в выбранной среде:

```sh
cd android
./gradlew --no-daemon clean assembleRelease lintRelease
```

APK появляется в `android/app/build/outputs/apk/release/`; проверяйте фактическое имя файла. Release-задача без `CHASOVOY_SIGNING_PROPERTIES` останавливается с ошибкой: unsigned release не считается допустимым результатом. Неполный/недоступный приватный файл или неправильный keystore также не дают подписанного выпуска. Наличие имени `release` в файле не заменяет проверку `apksigner`.

У выпуска должны быть `versionName = 1.0.1`, `versionCode = 102`, ожидаемый `applicationId` и постоянный сертификат. Не изменяйте `applicationId` ради обычного обновления. Новый release-сертификат не совместим с ранее установленными debug-сборками; пользователь должен заранее экспортировать нужные проекты и дневник питания, если потребуется переустановка. Экспорт показателей является отчётом: обратного пользовательского импорта в 1.0.0 нет.

## Проверки артефакта

Сопровождающий обязан проверить финальный APK после последнего изменения исходников/ресурсов. Для debug-кандидата базовая команда проекта — `clean assembleDebug lintDebug`; подписанный release дополнительно должен быть собран и проверен в своём варианте.

1. Gradle завершился успешно, lint-предупреждения изучены, ошибок нет. Запишите фактические команды и итоги.
2. Через Android SDK tools прочитайте пакет, `versionCode`/`versionName`, min/target SDK и полный список разрешений.
3. Проверьте подпись и SHA-256 сертификата с помощью `apksigner verify --verbose --print-certs <apk>`.
4. Проверьте ZIP alignment с помощью `zipalign -c -v 4 <apk>`.
5. Сравните встроенные assets APK с исходными байтами и реестром пакетов: путь, размер, SHA-256, идентичность. Проверьте также шаблон редактора и его четыре закреплённых файла.
6. Просмотрите DEX/строки на недопустимые firmware/OTA/reset/неограниченные командные пути и удостоверяйтесь, что остаточные строки не открывают вызываемый путь. Один поиск строки не является исчерпывающей проверкой поведения.
7. Проверьте, что публичный артефакт не содержит ключей, keystore, личных логов, устройств, health-records и домашнего пути разработчика.
8. Посчитайте SHA-256 итогового APK и его публикуемой копии. Зафиксируйте одну конкретную копию вместе с сертификатом и версиями инструментов.

Примеры независимых команд, где инструменты SDK должны быть в `PATH`:

```sh
apkanalyzer manifest application-id app-release.apk
apkanalyzer manifest version-name app-release.apk
apkanalyzer manifest permissions app-release.apk
apksigner verify --verbose --print-certs app-release.apk
zipalign -c -v 4 app-release.apk
```

Для SHA-256 PowerShell: `Get-FileHash -Algorithm SHA256 -LiteralPath <apk>`. Используйте реальный файл и сохраните фактический результат; хеш из документа не заменяет чтение своего артефакта.

В публичном пакете используйте переносимую проверку из корня:

```sh
python tools/verify_public_assets.py --root . --apk android/app/build/outputs/apk/release/app-release.apk
```

Для debug подставьте путь `android/app/build/outputs/apk/debug/app-debug.apk`. Скрипт сравнивает asset manifest, реестр встроенных пакетов и закреплённые файлы редактора с исходниками и содержимым конкретного APK. Он не подключается к часам, не заменяет lint, проверку подписи/разрешений и физическую приёмку.

Другие инструменты проверки могут требовать дополнительных входов. Для публичного пакета используйте приведённую выше команду; подробности — в [карте инструментов](DEVELOPER_GUIDE.md#автономные-инструменты-и-исходные-ресурсы).

Внутренний код 102 сохранён для обновления поверх проверенного кандидата. Публичный номер выпуска — 1.0.1; подпись совпадает с 1.0.0.

## Повторяемость

Повторяемая сборка APK из сохранённых assets означает наличие всех Gradle/Java/XML/PNG/`.dial` входов и совпадение их хешей. Она не обещает побайтово одинаковый APK при любом SDK, сертификате, времени ZIP и среде. Для такого обещания нужен отдельный протокол воспроизводимости.

Пересоздание галереи из исходных изображений, кадров и базовых пакетов — отдельный процесс. Не запускайте генераторы автоматически при Gradle-сборке; сначала проверьте доступность и права на все входы. Подготовка собственного проекта на телефоне использует встроенный закреплённый шаблон и не требует внешних генераторов.
