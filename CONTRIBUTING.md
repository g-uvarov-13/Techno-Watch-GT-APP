# Участие в разработке

Перед изменениями прочитайте [DEVELOPER_GUIDE.md](DEVELOPER_GUIDE.md), [BUILDING.md](BUILDING.md) и [KNOWN_LIMITATIONS.md](KNOWN_LIMITATIONS.md). Исходники протокола и встроенные пакеты требуют особенно узких изменений: GT01 не предоставляет этому проекту универсальную публичную спецификацию.

## Сообщение об ошибке

Укажите версию APK, версию Android, модель часов/прошивки в обезличенном виде, действие, ожидаемый результат, фактический итог и безопасный код ошибки. Разделите «видел на физическом устройстве», «воспроизвёл в эмуляторе» и «нашёл по коду».

Не добавляйте ключи API, закрытый сертификат, адрес устройства, личный маршрут, показатели здоровья или полный диагностический архив в публичную задачу. Сначала извлеките минимальные обезличенные данные. Для неизвестного формата нужен исходный образец с правом использования и понятным происхождением; строка из дампа не доказывает безопасный вызов.

## Работа над изменением

1. Сформулируйте поведение и границы изменения. Прочитайте затрагиваемый путь вызовов, активную политику и текущий реестр ресурсов.
2. Запишите небольшой план и назначьте владельца каждого изменяемого участка. Сохраните чужие правки. Не запускайте нескольких редакторов одной области.
3. Для нового протокольного поведения сначала получите архитектурный разбор: доказательства, точные файлы/байты, переходы состояний, стоп-условия и проверки. Реализация начинается после принятия этого разбора.
4. Тесты создаются, меняются или запускаются только при прямом запросе в текущей задаче. При отсутствии такого запроса запишите причину и используйте инспекцию, статические/синтаксические проверки, lint и разрешённую сборку.
5. Перед заявлением о готовности прочитайте итоговый diff и требования, выполните подходящие свежие проверки и укажите результаты проверки в описании изменения.
6. Для APK проверьте версии, разрешения, подпись, alignment, встроенные хеши и запрещённые командные пути. Сетевой успех и физическое принятие отмечаются отдельно.

Изменение только документации не требует сборки APK. Android-сборка не разрешает генерировать frontend, изменять иконки или пересоздавать галерею. Пользовательское ограничение текущей задачи имеет приоритет над общей рекомендацией инструмента.

## Стандарты реализации

Следуйте существующему разделению service/session/protocol/controller/store. Не добавляйте зависимость, generic abstraction или новый permission без конкретной необходимости. Валидация, отказ, атомарность публикации и сохранение пользовательских данных входят в функцию, а не остаются на неопределённое будущее.

Пишите комментарии для неочевидных ограничений и правил: проверенный донор, неизменяемый диапазон ресурса, причина запрета повторения, единица raw-поля, жизненный цикл подписки, политика прямой установки. Не заменяйте понятные имена комментариями, повторяющими синтаксис.

Не синтезируйте показатели для пустых графиков. Предпросмотры явно используют примерные данные. Сетевые ошибки классифицируйте без ключей и тел запросов. «Ошибка до HTTP» не должна отображаться как «неверный ключ».

Для архивов проверяйте имена, границы, размер распаковки, дубли, CRC/SHA и схему до публикации. Для БД используйте аддитивную миграцию и транзакции; не уничтожайте пользовательские данные при ошибке открытия. Для UI сохраняйте ввод и различайте текущую страницу, detail screen, scroll и async generation.

## Циферблаты и ресурсы

Изменяйте производную копию с новым хешем, сохраняя подтверждённый исходник. Сверяйте идентичность пакета, все локали, PLB/PGF-структуру и неизменяемые ресурсы. Четвёртое поле CR02 и единица native timing остаются неизвестными, пока нет нового доказательства.

Собственный код Giperion(BRM) распространяется под PolyForm Noncommercial 1.0.0. Проект предоставляет исходники для разрешённого некоммерческого использования; его нельзя обозначать как OSI open source. Коммерческое использование требует отдельного разрешения правообладателя. Проверяйте точный `LICENSE` и сведения о сторонних ресурсах перед распространением своей версии; неизвестные права оставляйте явно неизвестными.

## Представление изменения

Описание начинается с проблемы и нового поведения, затем содержит проверку и остаточный риск. Для небольшой правки достаточно нескольких предложений; для нового автомата нужны конкретные переходы/отказы и доказательства. Документация должна соответствовать фактическим итоговым файлам, а не промежуточному плану.

Не публикуйте pull request, push, релиз, комментарий во внешней системе или эксперимент на часах без нужного явного разрешения. Сначала доведите локальный результат до проверяемого состояния. Разрешение владельца часов на один target не относится к другой команде, прошивке или пакету.

Приватные материалы работы с нейросетями (инструкции агентам, запросы, переписка, планы задач, телеметрия и журналы) не добавляются в Git и не публикуются.
